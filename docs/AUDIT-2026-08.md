# CrunchyList — Audit & Google TV Pivot

**Date:** 2026-08-07
**Audited commit:** `6b958ba` (2026-03-01, last commit on `main`)
**Status:** Chrome extension works as built. Project blocked on delivery to the TV. Pivot required.

This document exists so the thread can be picked up cold. It covers what was built, why
work stopped, what's actually wrong with the code, and what carries over to a Google TV app.

---

## 1. Current state

A Manifest V3 Chrome extension — ~965 lines of vanilla JavaScript across four files, no
build step, no bundler, no dependencies. Built over three days (2026-02-27 → 2026-03-01),
18 commits, then stopped.

| Component | File | Role |
|---|---|---|
| Kid-facing tile grid | [`landing.js`](../extension/landing.js) | Overrides the new-tab page; renders whitelisted shows |
| Parent settings | [`options.js`](../extension/options.js) | PIN-gated; paste a CR series URL → auto-fetch title + poster |
| Navigation enforcement | [`background.js`](../extension/background.js) | `webNavigation` listener; redirects non-whitelisted URLs |
| Page stripping | [`content.js`](../extension/content.js) / [`content.css`](../extension/content.css) | Hides nav, search, recommendations, comments on CR pages |

**The intent is well documented.** [`CRUNCHYLIST-REQUIREMENTS.md`](CRUNCHYLIST-REQUIREMENTS.md)
is a solid spec that correctly identifies the problem: Crunchyroll's built-in controls are
too blunt in both directions — too much fan service gets through, while age-appropriate
shows get blocked. It is also honest about its own weak points in its "Open Questions"
section. That spec is still the product north star; only the *delivery mechanism* in it is dead.

## 2. Why work stopped

The last five commits tell the whole story:

```
7bccef1  Add Cast to TV button on watch pages
cf66608  Fix CSP violation: call Remote Playback API directly from content script
3ec4535  Remove Remote Playback attempt — CR player is in cross-origin iframe
b991ea2  Move cast button inside player iframe to preserve user gesture
cecb4da  Remove cast button — CR's DRM blob streams block all casting APIs
```

Step 4 of the spec's Expected Workflow was: *"They hit play, then cast to the Google TV via
the native Chromecast button in CR's player."* The entire product depended on that step.

It does not exist:

- Crunchyroll removed Chromecast from their web player (`b7b8609`).
- CR's Vilos player lives in a cross-origin iframe on `static.crunchyroll.com`, so a content
  script on `www.crunchyroll.com` cannot reach the `<video>` element (`3ec4535`).
- CR delivers video via MediaSource Extensions (`blob:` URLs) for Widevine DRM, which makes
  the Remote Playback API auto-dismiss instantly (`cecb4da`).

Four separate approaches were tried and the conclusion was correct. **The filtering was not
the failure — the delivery to the TV was.** Stopping was the right call.

## 3. Code audit

Findings in priority order. The theme: **the filter fails open in several places**, which is
the wrong default for a parental control.

### 3.1 Fail-open on empty whitelist — HIGH

[`background.js:45`](../extension/background.js#L45)

```js
if (ids.size === 0) return true;
```

An empty whitelist allows *all* of Crunchyroll. On a fresh profile where `chrome.storage.sync`
hasn't populated yet, this is a wide-open window during the exact period a parent assumes the
extension is protecting them. Should fail closed: no whitelist → allow nothing but the
landing page.

### 3.2 `/watch/` URLs are never blocked by the background script — HIGH

[`background.js:60-69`](../extension/background.js#L60)

Both branches return `true` — with tab context (lazy whitelist hit) *and* without
("For now, allow navigation and let content.js handle validation"). Every enforcement decision
on watch pages is therefore delegated to the content script.

### 3.3 The content script also fails open — HIGH

[`content.js:44`](../extension/content.js#L44)

> `// If we couldn't extract a series ID, we still allow the page`

Combined with 3.2, there is no layer that blocks a `/watch/` URL when series-ID extraction
fails. The two-layer design from the spec collapses to zero layers in that case.

### 3.4 Series-ID extraction can approve the wrong show — HIGH

[`content.js:95-99`](../extension/content.js#L95)

The final fallback grabs the first `a[href*="/series/"]` link on the page. On a watch page
that is very likely a *recommendation* link pointing at a different series. If that other
series happens to be whitelisted, a non-approved episode is waved through.

Related: the step-1 meta-tag scan at [`content.js:53`](../extension/content.js#L53) iterates
*all* meta tags and returns the first `/series/` match, preempting the more reliable explicit
`og:url` check at step 2. The fallback chain is not ordered by reliability.

### 3.5 Lazy-whitelist state is lost when the service worker sleeps — HIGH

[`background.js:15`](../extension/background.js#L15)

```js
const tabSeriesContext = new Map();
```

MV3 service workers are terminated after roughly 30 seconds idle. The `Map` is wiped with it,
so tab→series context silently disappears mid-session and watch pages fall through to the
allow-anyway path in 3.2. Needs `chrome.storage.session`.

### 3.6 Redirects are not blocks — MEDIUM

`onBeforeNavigate` + `chrome.tabs.update` does not cancel the navigation. The page begins
loading and can flash content before the redirect lands. The spec called for
`declarativeNetRequest`; it was never wired up and the permission is absent from
[`manifest.json`](../extension/manifest.json).

### 3.7 The PIN is decorative — MEDIUM (by design, but should be stated plainly)

[`options.js:10-16`](../extension/options.js#L10) — unsalted SHA-256 over a 4-digit PIN is
10,000 candidates, trivially reversed. But that is beside the point: any kid can open
`chrome://extensions` and toggle the extension off entirely. The README already concedes this
requires Chrome enterprise policy to mean anything. Worth keeping, but it is a speed bump,
not a control.

Also: no PIN reset path short of clearing extension storage.

### 3.8 Data inconsistency — LOW

[`whitelist.json`](../extension/whitelist.json) ships SPY x FAMILY as `G4PH0WXVJ`. The
[README](../README.md) and [requirements doc](CRUNCHYLIST-REQUIREMENTS.md) both cite
`GEXH3WKP7`. One is wrong; verify against the live CR URL before either is trusted as a
reference example.

### 3.9 Whitelist re-seeds itself — LOW

[`landing.js:14-22`](../extension/landing.js#L14) re-seeds the bundled default any time the
whitelist length hits zero. Remove all your shows and SPY x FAMILY reappears on next landing
page load.

### 3.10 MutationObserver is unthrottled — LOW (perf)

[`content.js:235`](../extension/content.js#L235) re-runs `hideElements()` on every mutation
batch with no debounce. `hideElements()` performs ~35 full-document `querySelectorAll` sweeps
plus a heading text scan, against a React SPA that mutates constantly.

### 3.11 Selector fragility — LOW (inherent, worth noting)

Broad wildcards like `[class*="banner"]`, `[class*="news"]`, `[class*="search-"]` and the
heading-text scan over `[class*="title"]` will collateral-damage CR's UI as their class names
change. The requirements doc already anticipated this and the code degrades gracefully rather
than breaking, which is the right trade — but it is permanent maintenance debt.

## 4. The Google TV pivot

**Goal:** a Google TV app on the home TV, kids pick from a parent-approved set of shows with
the remote, no computer involved.

### 4.1 The hard constraint

**You cannot build a TV app that plays Crunchyroll video.** There is no public playback API,
and Widevine licensing is bound to Crunchyroll's own client. This is the same wall as
`cecb4da`, and it is load-bearing — it is not a "figure it out later" item.

Therefore a Google TV CrunchyList cannot be a player. It must be a **launcher plus a guard**.

### 4.2 Architecture

**1. Tile-grid launcher.** Android TV app (Kotlin + Compose for TV), D-pad navigable, large
focus targets.

> **Constraint found 2026-08-07:** Android TV / Google TV does **not** allow a third-party app
> to be set as the default `HOME` launcher. Sideloaded launchers (Projectivy, FLauncher, AT4K)
> all work around this by **remapping the Home button via an AccessibilityService**. Google TV
> keeps running underneath.
>
> This changes the design in a useful way: the accessibility service is needed for the guard
> (§4.2.3) *anyway*, so it does double duty — Home-button remap **and** watchdog. One service,
> two jobs. But it also means the guard is now load-bearing for basic navigation, not just
> enforcement, so it cannot be treated as optional hardening.

**2. Hand-off into the official Crunchyroll app.** Tile click fires an `Intent` targeting the
CR app. **Verified working 2026-08-07 (§5.1)** — this is no longer a risk:

```kotlin
// series page
startActivity(Intent(Intent.ACTION_VIEW).apply {
    data = "crunchyroll://series/$seriesId".toUri()
    setPackage("com.crunchyroll.crunchyroid")
})

// or straight into playback of a specific episode
data = "crunchyroll://episode/$episodeId".toUri()
```

Path-only — do **not** include the host, it silently degrades to CR's home screen.

**3. A guard — ✅ PROVEN VIABLE 2026-08-07. `UsageStatsManager`, no AccessibilityService.**

### Why a guard is required after all

Briefly descoped on the theory that the kids wouldn't wander. That descope was withdrawn once
two holes were confirmed by test — **without a guard, CrunchyList filters nothing**:

1. **Back exits into the full catalogue.** From a tile: `ShowDetailsActivity` → Back →
   `MainActivity` (CR's home). Tried `NEW_TASK|CLEAR_TASK` to make the series page the task
   root — **no effect**; CR navigates to its own home internally, so no launch flag fixes it.
2. **CR can be launched directly** from the Google TV app menu. Attempted to hide it by
   disabling only CR's launcher entry (`.splash.ui.SplashActivity`) while leaving the
   deep-link target (`.main.ui.MainActivity`) intact — **blocked by Android**:
   `SecurityException: Shell cannot change component state`. Not possible via adb.

### The mechanism that works

A plain foreground app — **no AccessibilityService** — using two pieces:

**Detection: `UsageStatsManager.queryEvents()`** returns `ACTIVITY_RESUMED` events carrying the
full activity **class name**, not just the package. That is exactly the granularity needed:

| CR activity | Verdict |
|---|---|
| `.showdetails.ui.ShowDetailsActivity` | approved |
| `.player.ui.PlayerActivity` | approved |
| `.main.ui.MainActivity` | browsing → bounce |
| `.startup.ui.StartupActivity` | cold launch → bounce |

**Enforcement: `startActivity()` + a BAL exemption.** The naive bounce is blocked —
`Background activity launch blocked! goo.gle/android-bal`, and note `startActivity()` returns
**without throwing**, so it fails silently. Declaring `SYSTEM_ALERT_WINDOW` fixes it; the
system then reports `BAL_ALLOW_SAW_PERMISSION` and the activity comes to the front.

### Verified end to end

Probe: [`tools/probe-usagestats/`](../tools/probe-usagestats/) (Gradle-free, zero dependencies).

```
# hole 1 — backing out of an approved show
19:19:38  FOREGROUND  ...showdetails.ui.ShowDetailsActivity   approved
19:19:46  FOREGROUND  ...main.ui.MainActivity                 -> BOUNCE
19:19:46  BAL_ALLOW_SAW_PERMISSION
          IN FRONT NOW: com.lastgenlabs.clprobe/.ProbeActivity

# hole 2 — launching CR straight from the app menu
19:20:41  FOREGROUND  ...startup.ui.StartupActivity           -> BOUNCE
19:20:41  (bounced ~130ms later, before CR's home ever rendered)
          IN FRONT NOW: com.lastgenlabs.clprobe/.ProbeActivity
```

**Both holes closed by the same mechanism.**

### Required grants (one-time, per device)

```bash
adb shell appops set <pkg> GET_USAGE_STATS allow
adb shell appops set <pkg> SYSTEM_ALERT_WINDOW allow
```

Neither is a normal install-time permission. Both also have Settings → Apps → Special access
screens; **whether those screens are reachable on the Streamer's Google TV UI is unverified** —
adb works regardless and is a one-time setup step.

### Known issues to handle in the real implementation

1. **~2s detection latency** at a 2s poll — the kid sees CR's home briefly before the bounce.
   Tunable; battery is irrelevant on a mains-powered box.
2. **Must not fight its own launches.** A legitimate deep link transits
   `MainActivity` → `ShowDetailsActivity`, and `MainActivity` is a bounce trigger. The guard
   needs a short grace period after CrunchyList itself fires an intent, or it will bounce its
   own navigation.
3. **The probe is an Activity; the real guard must be a foreground Service** to survive being
   backgrounded. Not yet verified.
4. **Coupled to CR's class names** — but it **fails closed**: an unrecognised class is treated
   as not-approved and bounces. If CR renames things, CrunchyList becomes unusable rather than
   permissive. That is the correct failure direction, and the opposite of the extension's
   fail-open bugs (§3.1–3.3).
5. **The guard must actually be running.** Force-stopping CrunchyList from Settings disables it.
   A boot receiver plus foreground service mitigates; nothing short of Device Owner prevents it.

### 4.2.4 Surviving a Crunchyroll rename

Two different kinds of identifier are in play, and **only one is actually at risk**:

| Identifier | Example | Origin | Risk |
|---|---|---|---|
| **Content IDs** | `G4PH0WXVJ` | CR's catalogue, via the series URL or CMS API | **Low.** Canonical catalogue keys; unaffected by app updates. A bad one 404s visibly (§5.1). |
| **Activity class names** | `.showdetails.ui.ShowDetailsActivity` | CR's APK internals | **Real.** Can change on any app update. |
| **URI verbs** | `series`, `episode` | CR's APK internals | **Real.** Same class of risk. |

The whitelist is built from content IDs, so **the whitelist itself is safe**. What can break is
the guard's notion of which screens are approved, and the deep-link verbs.

Three layers, verified available on 2026-08-07:

**1. Version watch — turn silent breakage into a visible alert.**
`PackageManager` reports CR's version (`versionCode=22350`, `versionName=3.67.0`). Store it;
when it changes, mark the calibration stale and re-verify. Cheap, and converts "silently stopped
working" into "tell the parent".

**2. Enumerate instead of hardcoding.**
With `<queries><package android:name="com.crunchyroll.crunchyroid"/></queries>` (required by
Android 11+ package visibility), `getPackageInfo(..., GET_ACTIVITIES)` returns all 13 of CR's
activities. So match heuristically — any CR activity whose name contains `ShowDetails` or
`Player` — rather than pinning an exact FQN. Survives package restructuring such as
`.ui.showdetails.DetailsActivity`. CR's names are currently **not obfuscated**, so this works
today.

**3. Self-calibration — the layer that survives obfuscation.**
The key insight: **CrunchyList controls the launch.** When it fires
`crunchyroll://series/{known-good-ID}`, whatever CR activity *settles* in the foreground **is**,
by definition, the approved series screen. Learn it at runtime instead of being told.

```
calibrate():
  fire crunchyroll://series/{reference ID}
  watch UsageStats; ignore transit through the cold-launch/home classes
  the class that settles  -> approved SERIES class
  repeat with crunchyroll://episode/{reference ID} -> approved PLAYER class
  nothing settles, or it settles on the cold-launch class
      -> the deep link itself broke; alert the parent, stay fail-closed
```

This is the strongest layer because it does not care what the class is *called*. If CR ever
ships R8-obfuscated activity names (`a.b.c`), heuristic matching dies but calibration does not.
It also covers the URI-verb risk with the same mechanism: if `series` stops working, nothing
settles, and calibration reports the failure.

Run calibration on first setup, on CR version change, and on a parent-triggered "re-verify"
button. Keep a reference series ID pinned for the purpose — ideally one from the parent's own
whitelist, so it is guaranteed to be entitled content.

**None of this can make the guard permissive.** Every failure path ends at fail-closed (issue 4
above): unknown class → bounce. The worst outcome of a CR rename is an app that needs
re-calibrating, never one that quietly stops filtering.

### 4.3 What carries over from the extension

**Carries over:**

> **⚠ Open issue found 2026-08-07 during implementation: the CMS API returns 403 from the
> device.** The same request with the same browser User-Agent returns 200 from `curl` on the
> desktop, but Android's `HttpURLConnection` gets `HTTP 403` at the token endpoint — almost
> certainly Cloudflare fingerprinting the client (TLS/HTTP2 stack), not the User-Agent.
>
> Consequence: **titles and poster art do not auto-populate on device.** The app degrades
> gracefully — the show is added with its ID as the title and a letter placeholder tile — but
> the grid is much less useful for a pre-reader without art. Not yet solved. Options, roughly
> in order of promise: try OkHttp with tuned headers/ALPN, fetch metadata on the parent's
> desktop and import it, or let the parent type a title and supply an image URL by hand.
>
> This also removes the ability to *validate* a series ID at add-time, which is why
> `parseSeriesId` now enforces Crunchyroll's `G`-plus-8 ID shape — a typo would otherwise be
> stored silently and only surface as a 404 inside the Crunchyroll app.

- **The CR metadata layer.** [`background.js:156-232`](../extension/background.js#L156) —
  anonymous token from `/auth/v1/token` (`grant_type=client_id&client_id=cr_web`), then
  `/content/v2/cms/series/{id}` for title and `poster_tall` artwork. **Verified working
  2026-08-07** (HTTP 200 with a browser User-Agent; a bare `curl` gets a 403 from Cloudflare
  UA-filtering, which is *not* the endpoint being dead). Ports to Kotlin/OkHttp almost line
  for line and gives the tile grid titles and poster art for free.
- **The whitelist data model** — `{ seriesId, title, url, dateAdded }` plus a separate
  `seriesId → imageUrl` map. Straight to Room or DataStore.
- **The product spec** — [`CRUNCHYLIST-REQUIREMENTS.md`](CRUNCHYLIST-REQUIREMENTS.md) minus
  its casting workflow.
- **The UX shape** — tile grid, PIN-gated parent settings, paste-a-URL to add a show.

**Dead:**

- All content hiding ([`content.js`](../extension/content.js),
  [`content.css`](../extension/content.css)) — no DOM to strip on TV.
- `webNavigation` interception — no URLs to intercept.
- The entire casting workflow.

Roughly: the enforcement half is discarded, the curation half survives.

## 5. The blocking unknown — resolve this first

**Does Crunchyroll's Android TV app accept deep links to a specific series?**

This is not publicly documented anywhere. Every downstream architecture decision depends on
the answer, and it is cheap to test empirically (~30 min with ADB against the actual TV).

**If deep links work:** the architecture in §4.2 is unlocked. Tile → series page in CR.

**If they don't:** the product degrades to "a menu that dumps you into Crunchyroll's home
screen," and the guard has to do all the work. That is a materially worse product and worth
reconsidering scope before building.

### Test procedure

**Automated:** [`tools/probe-deeplinks.ps1`](../tools/probe-deeplinks.ps1) runs the whole
sequence — locates the CR package, dumps its intent filters, fires four deep-link variants
(https, https+locale, `crunchyroll://` scheme, scheme+host), records the resumed activity
after each, and screenshots the result. Works against the emulator or the physical Streamer.

```bash
.\tools\probe-deeplinks.ps1
```

Output lands in `tools/probe-out/` (gitignored). Verdict guide is printed at the end.

**Manual equivalent**, for reference — prerequisites in §6:

```bash
# 1. Pair with the TV (enable Developer Options → USB/network debugging first)
adb connect <tv-ip>:5555

# 2. Find the Crunchyroll package name — do not assume it matches the mobile app
adb shell pm list packages | grep -i crunchy

# 3. Pull the APK and dump its intent filters
adb shell pm path <package>
adb pull <apk-path> cr.apk
aapt dump xmltree cr.apk AndroidManifest.xml | grep -A20 -i "intent-filter"

# 4. Try an https app link at a known series
adb shell am start -a android.intent.action.VIEW \
  -d "https://www.crunchyroll.com/series/GEXH3WKP7/spy-x-family" <package>

# 5. Try a custom scheme if the manifest shows one
adb shell am start -a android.intent.action.VIEW -d "crunchyroll://series/GEXH3WKP7" <package>
```

**What to record:** whether the app opens at all, whether it lands on the *series page* or
just the home screen, and whether a `/watch/` episode link goes straight into playback.
The manifest dump in step 3 is the authoritative answer — steps 4-5 confirm it behaves.

## 5.1 RESULTS — run 2026-08-07

Against the `crunchylist_tv` emulator (Google TV, API 36) with Crunchyroll
`com.crunchyroll.crunchyroid` installed from the Play Store.

### Established (from the manifest — not inference)

The CR TV app declares **exactly one** `VIEW` + data intent filter:

```
com.crunchyroll.crunchyroid/.main.ui.MainActivity  filter a34c1d3
  Action:   "android.intent.action.VIEW"
  Category: "android.intent.category.DEFAULT"
  Scheme:   "crunchyroll"
```

1. **❌ No https app links.** There is no `https` / `www.crunchyroll.com` filter anywhere in
   the package. Both https probes failed outright:
   `Error: Activity not started, unable to resolve Intent`.
   **The manual procedure in §5 above, which used an https URL, would never have worked.**
2. **✅ `crunchyroll://` custom scheme is declared and accepted.** Both scheme probes launched
   with no resolve error — the app comes to the foreground.
3. **⚠️ The filter declares no `Authority:` and no `Path:`.** It matches *any* `crunchyroll://`
   URI; all routing happens inside the app. **The URI grammar is therefore not discoverable
   from the manifest** — it has to be found by experiment, or by decompiling the APK.
4. **No `BROWSABLE` category** — only `DEFAULT`. So the scheme can't be triggered from a web
   browser, but *can* be fired by another app via an explicit Intent. That is exactly our case,
   so it is not a problem.

### ✅ RESOLVED — deep links work. Architecture is unlocked.

With a signed-in Crunchyroll account, `crunchyroll://series/G4PH0WXVJ` lands directly on the
**SPY x FAMILY show-details page** — correct art, description, rating, episode list, and
`CONTINUE: E1 — 1h 49m left`. Native resume state is preserved, which the original spec
(§Expected Workflow step 6) called for.

### Confirmed URI grammar

| URI | Resumed activity | Result |
|---|---|---|
| `crunchyroll://series/{SERIES_ID}` | `.showdetails.ui.ShowDetailsActivity` | ✅ **series page** |
| `crunchyroll://episode/{EPISODE_ID}` | `.player.ui.PlayerActivity` | ✅ **straight into the player** |
| `crunchyroll://watch/{id}` | `.main.ui.MainActivity` | ❌ not a route — falls back to home |
| `crunchyroll://media/{id}` | `.main.ui.MainActivity` | ❌ not a route |
| `crunchyroll://www.crunchyroll.com/series/{ID}/{slug}` | `.main.ui.MainActivity` | ❌ **host segment breaks it** |
| `https://www.crunchyroll.com/series/{ID}/{slug}` | (launcher home) | ❌ no filter — `unable to resolve Intent` |

**Two rules that matter:**

1. **Path-only, no authority.** `crunchyroll://series/{ID}` works; putting the host in
   (`crunchyroll://www.crunchyroll.com/series/...`) silently degrades to the app's home screen.
   Note the web path segment is `/watch/` but the *scheme* verb is `episode` — they do not match.
2. **Episode-level deep linking exists** and goes straight to `PlayerActivity`. This materially
   changes open decision #2 (§7): per-episode control is available, not just per-series.

### Side effect: audit finding 3.8 is resolved

The first probe used `GEXH3WKP7` (the ID in the README and requirements doc) and the app
returned **`Error Code: 404`**. `G4PH0WXVJ` — the ID in
[`whitelist.json`](../extension/whitelist.json) — is the correct one.

**The README and CRUNCHYLIST-REQUIREMENTS.md both cite the wrong series ID and need fixing.**
The 404 is also a useful signal in itself: the app genuinely resolves the ID against CR's
backend rather than opening a generic page, so a bad whitelist entry fails loudly.

### Bonus finding — possibly a better mechanism than deep links

The dump also shows the app is a **Google Cast Connect receiver**:

```
.player.ui.PlayerActivity   Action: "com.google.android.gms.cast.tv.action.LOAD"
.main.ui.MainActivity       Action: "com.google.android.gms.cast.tv.action.LAUNCH"
.main.ui.MainActivity       Action: "android.intent.action.SEARCH"
```

`cast.tv.action.LOAD` is the documented Cast Connect entry point for loading specific media by
content ID into a receiver app's player.

### ❌ Cast Connect ruled out — tested 2026-08-07

**This was investigated and does not work.** Firing the LOAD intent locally — both
package-scoped and with an explicit component — **hard-crashes the Crunchyroll app**:

```
W ReceiverMediaUtils: The intent is not a Cast resume session intent
E AndroidRuntime: java.lang.IllegalStateException: Required value was null.
      at com.crunchyroll.crunchyroid.player.ui.PlayerActivity.G2(PlayerActivity.kt:51)
      at com.crunchyroll.crunchyroid.player.ui.PlayerActivity.onCreate(PlayerActivity.kt:98)
W ActivityManager: Process com.crunchyroll.crunchyroid has crashed too many times, killing!
```

The activity launches, CR's own `ReceiverMediaUtils` rejects the intent as "not a Cast resume
session intent", and a Kotlin non-null assertion then fails on session state that only the Cast
framework populates.

Three reasons this is a dead end, not a "needs more extras" problem:

1. **Structural mismatch.** Cast Connect is a *sender → receiver* protocol across two devices.
   CrunchyList runs **on** the TV. There is no sender, and casting to yourself is not the model.
2. **Session state, not just extras.** The failure is missing Cast *session* context, not a
   missing content ID. We cannot synthesise that by guessing intent extras.
3. **No durability benefit anyway.** Reverse-engineering Cast session internals would be
   *more* undocumented than `crunchyroll://`, not less — which defeats the entire reason for
   considering it.

**Conclusion: `crunchyroll://` is the mechanism.** It is undocumented and CR could change it,
but the mitigation is cheap — re-run `tools/probe-deeplinks.ps1` after a CR app update and the
grammar re-verifies in about a minute.

`android.intent.action.SEARCH` on MainActivity remains an untested third route (launch a search
for the series title) — cruder, and only worth exploring if the scheme ever breaks.

> **Gotcha for future setup:** `Expand-Archive` fails on the cmdline-tools zip when the
> destination path is long — the guava `listenablefuture-9999.0-empty-to-avoid-conflict-with-guava.jar`
> entry blows past Windows' 260-char `MAX_PATH`. Extract from a short path.
>
> **Gotcha for screenshots:** never pipe `adb exec-out screencap -p` through PowerShell `>`.
> It applies text encoding and prepends a BOM, corrupting the PNG. Use
> `[IO.File]::WriteAllBytes()` or redirect from bash.
>
> **Gotcha for Gradle — cost several hours to diagnose, read this first.** Gradle fails on
> this machine with:
> ```
> java.io.IOException: Unable to establish loopback connection
> ```
> This is **not** a network, firewall, port-exclusion or antivirus problem, and it is not
> Gradle's fault. Root cause: on this machine `AF_UNIX connect()` returns
> `Invalid argument` for sockets under `C:\Users\...\AppData\Local\Temp`, while working
> normally in other directories. JDK 21's NIO selector (`WEPollSelectorImpl` → `PipeImpl`)
> builds its wakeup pipe as an AF_UNIX socket pair in the temp dir, so `Selector.open()`
> throws — and Gradle can never reach the daemon it just started.
>
> Diagnosis path, if it ever resurfaces: `Selector.open()` fails while `Pipe.open()` and plain
> TCP loopback both succeed; the stack trace bottoms out at
> `sun.nio.ch.UnixDomainSockets.connect0`. An AF_UNIX bind+connect test succeeds under
> `C:\AndroidProjects` and fails under `AppData\Local\Temp`, which isolates it to location.
>
> **Fix:** point `TEMP`/`TMP` outside `AppData\Local\Temp` *before the JVM starts*.
> `-Djava.io.tmpdir` and `-Djdk.nio.channels.unixdomain.tmpdir` are **not sufficient** — the
> location is resolved too early for them. [`tv-app/build.sh`](../tv-app/build.sh) wraps this;
> use it instead of calling `gradlew` directly.
>
> **Gotcha for input:** the `tv_1080p` AVD profile has **no touchscreen** (real TVs aren't
> touch devices), so mouse clicks on the emulator screen — including on the on-screen
> keyboard — do nothing. It also ships `hw.keyboard = no`, so the physical keyboard isn't
> forwarded either, which makes the Google sign-in screen appear completely dead.
>
> Fix in `~/.android/avd/<name>.avd/config.ini`:
> ```ini
> hw.keyboard = yes
> hw.gpu.enabled = yes
> hw.gpu.mode = host
> ```
> Restart the emulator afterwards. Navigate with **arrow keys** (D-pad), **Enter** to select,
> **Esc** for Back. `hw.gpu.enabled = no` is also the default and makes it render in software —
> enabling it cut boot from 20s to 15s and makes the UI far more responsive.

### 6.1 Emulator instead of hardware

The physical Streamer is not always on hand. An **Android TV AVD** covers most of §5:

| Question | Emulator can answer? |
|---|---|
| Does the CR app declare deep-link intent filters? | ✅ yes — `dumpsys package` |
| Does a series deep link land on the right screen? | ✅ yes |
| Building / iterating the launcher UI | ✅ yes, and faster than hardware |
| Does video actually **play**? | ❌ no — emulators have no Widevine L1 and CR will likely refuse |
| Does launcher replacement work on the real box? | ❌ no — device policy is hardware-specific |
| Is Device Owner provisioning possible? | ❌ no — needs the real device |

So the emulator resolves the **blocking unknown** (§5) and unblocks all UI work. The
hardware-policy questions stay open until the Streamer is available. That is an acceptable
split — the deep-link answer is the one that gates architecture.

**Note:** the CR app must be installed from the Play Store on a Play-enabled Android TV system
image. Do not sideload the APK from a third-party mirror.

## 7. Open decisions

1. ~~**Which device?**~~ **RESOLVED 2026-08-07: Google TV Streamer 4K.** Google-made, stock
   Android TV OS 14, 32 GB. Implications:
   - **Sideloading:** straightforward via `adb install`.
   - **Custom HOME:** not directly settable — see the constraint box in §4.2.
   - **Device Owner / lock-task:** likely **off the table**. `dpm set-device-owner` requires
     *no accounts on the device*, but a Google account is needed for the Play Store to install
     Crunchyroll. Theoretically sequenceable (factory reset → skip account → set device owner →
     sign in), but it depends on Google TV's setup wizard allowing account skip, and testing it
     costs a factory reset. **Assume watchdog-only enforcement** unless there's appetite for
     that experiment.
   - **ADB:** network only (`adb connect <ip>:5555`); the USB-C port is power. Enable via
     Settings → System → About → *Android TV OS build* ×7, then Developer options → USB
     debugging (or Wireless debugging, which uses the newer pairing-code flow).
2. ~~**Guard fidelity.**~~ Moot — guard descoped (§4.2). What survives is a **product** question,
   not an enforcement one: **where should a tile go?**
   - `crunchyroll://series/{ID}` → CR's show page. Kid picks the episode; CR's own
     `CONTINUE: E{n}` resume button is right there. Simple, and matches the current whitelist
     model exactly.
   - `crunchyroll://episode/{ID}` → straight into playback. Fewer button presses, but
     CrunchyList would have to track which episode is next per show, duplicating state CR
     already keeps correctly.

   **Recommendation: series-level.** CR already solves resume, and duplicating that is work
   with a real chance of getting out of sync.
3. **Does the extension stay alive?** It still works on a laptop. Keep it maintained as a
   sibling product, or freeze it and treat this repo as TV-only?
4. **Repo shape.** A Kotlin Android app alongside `extension/` means Gradle, a build step, and
   the end of the "clone and load unpacked" simplicity the spec valued. Monorepo with
   `extension/` + `tv-app/`, or a separate repo?
